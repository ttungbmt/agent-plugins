# agent-plugins

`ap` reads a Config (`agent-plugins.yaml`) and syncs marketplaces, plugins, skills, agents, rules, workflows, MCP
servers and hooks into a Claude Code Scope.

## Commands

Run from the repo root; `mise install` provides Node and pnpm.

- `pnpm -C packages/cli test` and `pnpm -C packages/cli typecheck` — the pre-commit gate. CI runs only on release
  tags, so this local run is the only one.
- `pnpm ap <args>` — rebuilds the CLI incrementally, then runs it (e.g. `pnpm ap sync --dry-run`).
- `pnpm -C packages/cli pack:release`, then `packages/cli/scripts/smoke-release.sh` — build and smoke-test the
  release tarball. Full release runbook: `docs/releasing.md`.
- `pnpm mcp:outdated` — list MCP catalog entries with stale version pins.

## Architecture

`packages/cli/src/sync/index.ts` orchestrates: `resolve.ts` loads the Config and its Presets (`preset-loader.ts`),
reads each one with `spec.ts` and merges them by Inheritance and Preset selection (`merge.ts`) → `plan*.ts`, `mcp.ts`
and `hooks.ts` compute actions → apply → `store.ts` writes Lock/State.
Every side effect goes through the `deps` argument (`exec`, `fetch`, `fetchSkillSource`, `homedir`), which is what
keeps the tests offline.

Two ADRs shape the code most; read the relevant ADR before changing how settings are written, how items are
installed, or how Lock/State is kept:

- **0001** — marketplaces, plugins and MCP servers are written by shelling out to the `claude` CLI; `ap` only patches
  settings afterwards.
- **0005** — `claude` has no command for skills, agents, rules or workflows, so `ap` fetches their sources with `git`
  and copies them into the Scope itself. Hooks are likewise written straight into settings (0007).

Extending it:

- Skills, agents, rules and workflows share one `ItemHandler` (`items.ts`), registered in `ITEM_KINDS` (`types.ts`) and
  `HANDLERS` (`index.ts`). A new item kind follows the same shape.
- A new `spec.*` key touches three places: `PRESET_SPEC_KEYS`/`CONFIG_SPEC_KEYS` and the parser in `spec.ts` (the
  only runtime validation, which rejects unknown keys), `schemas/config.schema.json` and `schemas/preset.schema.json`.
  `spec-schema.test.ts` names whichever one was missed.

## Testing

- Sync tests run against `fakeClaude` (`fake-claude.ts`), which mimics a specific `claude` CLI version, and build
  fixtures with `makeTree` (`test-helpers.ts`). When real `claude` behaves differently, update the fake first.
- Each kind has its own `sync-<kind>.test.ts` covering all three Scopes; `sync-mcp.test.ts` is the template.

## Environment

An applying `ap sync` needs `claude` and `git` on `PATH` (`--dry-run` and `--check` skip `claude`), and it writes to
Claude Code's live config — `--scope user` means your own `~/.claude`. Run applying syncs in the Docker sandbox
(`docker compose run --rm ap`, see `docker/README.md`) or with `CLAUDE_CONFIG_DIR` pointed at a scratch directory.

## Gotchas

- This repo dogfoods `ap`: `.claude/` and `agent-plugins.lock` at the root are generated from the `agent-plugins`
  preset. Change the preset and run `pnpm ap sync` instead of editing them by hand. The exception is the files
  directly in `.claude/rules/`: they are hand-written Manual entries that `ap` never touches.
- The git fetcher every item kind uses lives in `sync/skills.ts` (`createGitFetcher`), not in a module of its own.
- After touching the MCP catalog (`packages/cli/presets/mcp-servers.yaml`), run `mcp-catalog.test.ts`.

## Conventions

Cross-project conventions (language, glossary, docs and ADRs, feature workflow, git, TS style) live in
`.claude/rules/`, written to be copied as-is into other projects — keep anything specific to `ap` in this file
instead. Commit scopes used here: `sync`, `cli`, `presets`, `schemas`, `release`.

Collection helpers (ADR 0016): reach for es-toolkit over hand-written array/object/predicate helpers, for readability
only — it is not faster here.

- Arrays → es-toolkit (`difference`, `uniq`, `partition`, `omit`, `pickBy`, …); an existing `Set` → its own methods;
  grouping → `Map.groupBy`; deep equality → `isDeepStrictEqual` from `node:util`.
- Never import `isEqual`, `compact`, `groupBy`, `sortBy`/`orderBy`, `kebabCase`, `memoize`, the `*Async` array helpers,
  `es-toolkit/server` or `es-toolkit/compat`; ADR 0016 says why for each.
- `packages/cli/src/es-toolkit-imports.test.ts` enforces that list and holds it; change the list there, nowhere else.
- Skip a replacement that needs a new cast or lets `any` through. Use the repo's `isRecord`, never `isPlainObject`.
